# Rankings (`irw_rank`, `source = "rank"`)

Processing scripts and records for the **rankings** data family (`source = "rank"`): tables in which each respondent places a fixed set of options in order. The first source is FairVote's cast vote records from US ranked-choice elections; the layout is written to also hold Scottish, Australian and Irish ballot data and survey ranking questions.

**Status (2026-10-15).** Draft standard with seven reference tables (`examples/`: six FairVote contests and one Eurovision jury show); 18 Eurovision tables built from `eurovision_jurors.py`; 14 non-FairVote tables from the second batch (`voter_autrement.py`, `atsusaka_2024_rcv_survey.py`, `atsusaka_2025_ranking_questions.py`, `scottish_stv.py`; helpers in `rank_common.py`). The family is live: the Redivis dataset `irw_rank` (display name `IRW_rank`, reference id `93f5`; `IRW_RANK_DATASETS` in `metadata/redivis_config.R`, a shard list from day one) holds the first tables, both packages accept `source = "rank"` and ship a `rank_compress` helper (below), `red_up --dataset irw_rank` runs the validator and the design-row gate, `metadata/18_rankings.R` writes `rank_metadata`, and `metadata/02_biblio.R` reads the dictionary file. The site page (`rankings_standard.qmd`) is planned. Tables are built and checked locally with the two commands below, and a table counts as done when it passes the validator and has its rows in `design_tables.csv`, `candidates.csv` and the dictionary. The rulings that shaped this standard are logged at the end; the structural scouting that found the family is in `oneoff/structure-scouting-2026-10-13/`.

```
python3 data/rankings/fairvote_cvr.py build <raw dir> <out dir> <table> [...]   # build FairVote tables
python3 data/rankings/eurovision_jurors.py build <raw dir> <out dir> --all        # build Eurovision juror tables
python3 data/rankings/voter_autrement.py build <raw dir> <out dir> --all          # French voting experiments 2017/2022/2024
python3 data/rankings/atsusaka_2024_rcv_survey.py build <raw dir> <out dir> --all # Alaska/Oakland ballot-order surveys
python3 data/rankings/atsusaka_2025_ranking_questions.py build <raw dir> <out dir>
python3 data/rankings/prd_rankings.py build <raw dir> <out dir> [<table> ...]     # Political Rankings Database survey rankings
python3 data/rankings/farvaque_2007_faches_irv.py build <raw dir> <out dir>      # 2007 French IRV voting experiment
python3 data/rankings/kerver_2021_prosthesis_items.py build <raw dir> <out dir>  # HealthFan top-10 item ranking
python3 data/rankings/scottish_stv.py build <raw dir> <out dir> 4_cands/aberdeen_2017_ward11.csv
python3 -m irw_validate.rankings --design data/rankings/design_tables.csv <out dir>/*.csv
```

## Scope

A table belongs here when each respondent orders a fixed set of named options: ranked-choice ballots (instant-runoff, single transferable vote, sequential), rank-order lists (school or job choice), survey questions that ask for a ranking, and judging panels where each judge ranks every entry (Eurovision jurors). The family is defined by the act of ranking, not by what is ranked (Ben, 2026-10-15). The options are the same things for every respondent and each appears once per ranking. The response is a **position**, not a score.

Not here: a comparison between two fixed things (competitions family); profiles assembled at random from attributes (conjoint family); a Q-sort, where positions are forced into a fixed shape with ties (a cousin, not in scope); a single pick from a list (core or nominal). Best-worst scaling belongs with the conjoint discrete-choice rules (#2978).

## Layout

One row per respondent × task × marked position. The core column names are kept so core tooling reads the table, but `resp` is a rank.

| column | |
|---|---|
| `id` | the ballot or respondent, re-keyed 1..n in source order. Never a voter identifier (cast vote records have none; a survey's panel ID is dropped). |
| `task` | which ranking, when a respondent gave more than one (several contests on one ballot, several ranking questions). `1` throughout a one-contest table. |
| `item` | the option ranked: a **candidate code** (`c01`, `c02`, …, below), the reserved values `(write-in)` and `(overvote)`, or, for options that are not people, the option text as shown. |
| `resp` | the position marked, `1` = first choice, **as recorded**. Positions are not renumbered after a skip: a ballot marked at positions 1 and 3 keeps `resp` 1 and 3. |
| `cov_<name>` | ballot- or respondent-level columns from the source, as text, repeated on every row of the ballot: `cov_precinct`, `cov_ballot_style`, `cov_counting_group`, `cov_district`, `cov_voting_location`. `fairvote_cvr.py` strips leading and trailing whitespace from their values (#3024). |
| `trial_<name>` | task-level details, if any (question order, survey arm). |

A source column is not a covariate, and is dropped, only when it is constant across the whole
source deposit. The name `cov_count` is reserved: a `Count` column in a cast vote record is the
number of identical ballots a row stands for, which belongs to the collapsed layout still
to be settled for the multi-million-ballot files, so `fairvote_cvr.py` drops `Count` while
it is identically 1 and stops if it ever is not (#3024).

Rules:

- **Skipped positions are not rows.** A skip is visible as a gap in `resp`. A ballot with no marks has no rows; the design record keeps `n_ballots_cast` and `n_ballots_with_marks` so denominators survive.
- **Duplicate marks are kept as recorded.** A candidate marked at positions 1 and 2 gives two rows with the same `item` and different `resp`. Counting rules for duplicates differ by jurisdiction (most treat the later mark as a skip); the user applies theirs, the table does not. This is the one departure from one row per `id × item`, and it is the reason a core-style pivot of a rankings table needs care. The package helpers `irw_rank_compress()` (R) and `irw.rank_compress()` (Python) drop an item's later marks and renumber positions `1..k` within each ranking; the reserved values are never dropped.
- **One position, one row, except ties.** An overvote is one row. Two items at the same position within `id × task` are a tie (equal ranks, as Debian ballots allow), kept as recorded; the validator reports `n_tied_ballots` as a warning (Ben, 2026-10-15: ties may exist, as in competitions).
- **`(overvote)`** is a row at the position where more than one candidate was marked; the source does not say which, so nothing else can be stored. **`(write-in)`** is a row with that item unless the source names the written-in candidate. Both are the one string in every table, like `(not shown)` in conjoint.
- **One contest per table**: one option set, one electorate, one date (ruling 4). A survey with several ranking questions is one table with `task` distinguishing them.

### Candidate codes

Candidate names are personal names in public records and are **not stored anywhere in the IRW** (Ben, 2026-10-15). Within a contest, the distinct names as printed in the source file are sorted case-insensitively (`key = (name.casefold(), name)`) and coded `c01`, `c02`, … with zero-padding to at least two digits (three when a contest has 100 or more candidates). The reserved values are excluded from the sort. Anyone holding the public source file can rebuild the mapping from this rule and the script; no name is written to the table, the script header, the design record or the dictionary. The validator (R4) refuses an item that looks like a personal name. Party, incumbency and other candidate attributes are not kept; if they are ever wanted they would be an item-level table built from the same rule, not names in `item`.

Options that are not people (policies, schools, products in a survey ranking) are stored as the text shown, as in other families. A party list in a list election is coded like a candidate (Voter Autrement 2024: five of the 38 official list labels carry a politician's name), and a covariate that names a candidate (a reported official vote) carries the same code as `item`.

## Intake rules

- **Licence:** CC0, CC BY, CC BY-SA or CC BY-NC, as elsewhere in IRW (a no-derivatives licence is not accepted); ODbL 1.0 is also accepted (attribution, derived database under ODbL), per the IRW licensing summary table (Ben, 2026-10-15). FairVote's three collections are CC0 1.0 throughout. Public election records are public records in their own right; the deposit's licence is what the dictionary carries.
- **At least 50 ballots with marks** per table. The core floor is 100 respondents; rankings use 50 rankers because a ranking over three or more objects contributes several positions, so 50 rankings carry at least as much information as 100 single responses on a short instrument (Ben, 2026-10-15). The validator warns below 50.
- **No voter identifiers.** A source's ballot ID or row index is dropped at re-keying.
- **Table names:** election tables are `rcv_<jurisdiction>_<yyyymmdd>_<office>`, lowercase, at most 40 characters, with the abbreviations in `fairvote_cvr.py` (`nyc`, `sf`, `mpls`, `council`, `boe`, `hd`, `bp`, …). Other rankings use the usual `author_year_topic`.
- **Size.** The largest FairVote files (New York City, San Francisco) are 100–125 MB wide and 2–3× that long, so they need the token upload path.
- **Uploading.** `red_up --dataset irw_rank <dir>`: a rankings table has `id`/`item`/`resp`, so only the destination tells `red_up` to run `irw_validate.rankings` (R1–R8 against `design_tables.csv`) instead of the core validator; a table with no design row is refused. New tables go to the newest shard (`RANK_DEFAULT` in `red_up/targets.py`).
- **Downloads are untrusted.** Scripts read only the files named in their header; nothing shipped with a deposit is executed.

## Records kept for every table

- **A script**, or for FairVote the table's row in `fairvote_manifest.csv` (the one script `fairvote_cvr.py` builds every FairVote table from its manifest row). A non-FairVote table gets its own script with the usual IRW header: citation, deposit DOI and licence, files read, what was dropped, and any count discrepancy with the source.
- **A design record:** one row in `design_tables.csv` (below). `fairvote_cvr.py` writes it; other scripts append theirs.
- **A dictionary row,** staged with `automated_finding/stage_dict_row.py --source rank`, which writes to `dictionary_auto_rank.csv`. `metadata/02_biblio.R` reads that file alone (no sheet, as conjoint) and publishes `rank_biblio`. Nothing rewrites that file after staging, so a `Notes` sentence about where the table is not yet -- "Not on Redivis yet." -- has to be cleared by hand in the PR that flips the ledger row to `uploaded`. `metadata/tests/test_rank_dictionary.py` fails when a live table still carries it.
- **A row in `candidates.csv`,** the ledger of every file or deposit considered (claims and quirks go to tracking issue #3024), with status `todo`, `built`, `uploaded` or `held: <reason>`.
- **A processing note** in `metadata/data_notes.csv`, once the table is on Redivis.

## Design record (`design_tables.csv`)

The tables share a layout but not a meaning: how many positions a ballot offered, how many seats were filled and which counting rule applied all change what a ranking means. One row per table; when no source states a fact the value is `unknown`, never a guess. `metadata/18_rankings.R` joins every column but `evidence` into `rank_metadata` (the record's `n_duplicate_marks` as `design_n_duplicate_marks`, beside the live count) and reports a record whose counts disagree with the live table.

| column | |
|---|---|
| `source_file`, `collection` | the file converted and the deposit DOI |
| `jurisdiction`, `date`, `office` | from the file name; `date` ISO |
| `rules_jurisdiction` | the key this table's counting rules are under in `counting_rules.csv`, when that is not its own `jurisdiction`; empty otherwise, which is the usual case. `jurisdiction` is the data key and names the contest as the source does, so a source that deposits one file per district carries one key per district while its counting rules are written once for the whole state. New South Wales is the first such source: its 279 rows hold 98 district keys and all of them read `New South Wales (Legislative Assembly)`. The chamber is part of the key because the rules differ by chamber (Ben, 2026-10-29, #3024). |
| `method` | `irv` (single winner), `stv` (proportional, multi-winner), `sequential` (multi-winner by repeated IRV), `survey`, `rank_order_list`, `jury` (a judging panel), or `unknown`. For FairVote, from which collection the file sits in. |
| `seats` | number of winners; `unknown` until filled from the jurisdiction's own documentation; `na` for a jury ranking |
| `n_positions` | positions offered on the ballot (K in `rank1..rankK`) |
| `n_candidates` | distinct candidate codes, excluding reserved values |
| `n_ballots_cast` | rows in the source file |
| `n_ballots_eligible_est` | ballots whose precinct has at least one marked ballot; equals `n_ballots_cast` when the file has no precinct column. New York City's exports list every ballot of the primary, including precincts where the contest was not on the ballot (District 49: 213 of 312 precincts have no marked ballot), so `n_ballots_cast` overstates the electorate there. The estimate is a floor on undervoting, not a turnout figure: precincts can straddle districts. |
| `n_ballots_with_marks` | ballots with at least one row; equals the table's number of ids |
| `n_duplicate_marks`, `n_overvotes`, `n_writeins` | counts of those rows |
| `write_in_allowed` | `yes` when the file has write-in marks, else `unknown` until documented |
| `candidate_order` | `fixed` (the same ballot order for every voter), `rotated` (the order varies across ballot styles, whether randomised per respondent or rotated systematically by precinct under statute), or `unknown`. A statute that governs the jurisdiction's ballots is enough; say in `evidence` when the value rests on statute rather than an observed ballot. |
| `evidence` | where each value came from |

`seats`, `write_in_allowed` and `candidate_order` are the fields that need a person: they come from the jurisdiction's election page or statute, and the same value usually holds for every contest of one jurisdiction and year. That is the collaborator task (`COLLABORATORS.md`).

## Counting rules (`counting_rules.csv`)

How a jurisdiction counted its ballots depends on the jurisdiction and the date, not on the table, so the rules are written once per rule set in `counting_rules.csv` rather than as columns of `design_tables.csv` (Ben, 2026-10-22, #3165). A table's rules are in the row whose `jurisdiction` is the table's `rules_jurisdiction`, or its `jurisdiction` where that cell is empty, and where `valid_from` <= `date` < `valid_to`, with both dates from `design_tables.csv`; an empty `valid_to` means no later text replaced the rule set in the texts saved. The first rows are Minneapolis 2009-2023, then Alaska from 2020, then the Debian Project from 2003, then the New South Wales Legislative Assembly from 1979. Other jurisdictions get rows when their rules are written down.

`valid_from` and `valid_to` are the dates a text was adopted: for Minneapolis the dates the city council adopted the ordinance text, for Alaska the date the voters adopted Ballot Measure 2 (3 November 2020). They are not effective dates. The Minneapolis sources give adoption and mayoral approval dates but no effective date; an Alaska initiative "becomes effective 90 days after certification" (AS 15.45.220). The join treats a text as in force from its adoption in both cases. That is a convention of this file, not a claim about when the text took effect. For Alaska, whose rule set rests on more than one text, `valid_from` is the earliest adoption among the texts that made the rule set (older texts they refer to, which `ordinance` cites without a date, are not counted), the row says which text each rule comes from, and `ordinance` gives the date of each text that a saved source dates (Ben, 2026-10-24, #3024); that cell-by-cell map opens `evidence`, so that `sections` stays a citation list. Debian is the exception: `valid_from` is the day after the ratification of the constitution version that made the rule set, and `valid_to` the `valid_from` of the next rule set, because a vote that closed on a ratification day was counted under the version before it (three of the 33 did, on 2007-10-07, 2022-01-28 and 2022-03-26). That is a claim about when a text took effect, so `ordinance` gives the ratification date itself (Ben, 2026-10-24, #3024). For New South Wales `valid_from` is the assent of the Act that inserted the Seventh Schedule of the Constitution Act 1902 (30 April 1979), an adoption date like the others: the count rests on the Schedule, and `duplicate`, the one cell that rests on the Electoral Acts, on texts that `ordinance` dates later.

The join matches one key exactly; it never matches a prefix of one. A jurisdiction whose rules are written once for many data keys names the key in the table's `rules_jurisdiction` instead, and the rule set is written under that one key. Matching `New South Wales` as a prefix of its 98 district keys would be shorter, but the keys are the labels the source's own files give and a prefix of one is not a statement about which text governs: `New South Wales` is a prefix of the Legislative Council's keys too, and that chamber counts by STV under different clauses. An exact key also leaves nothing to decide when two rows could match (Ben, 2026-10-29, #3024).

| column | |
|---|---|
| `jurisdiction` | as in `design_tables.csv` |
| `rule_set` | a name for the rule set (`mpls_2009`, `mpls_2013`, `mpls_2015plus`, `ak_2020plus`, `debian_2003`, `debian_2015`, `debian_2022plus`, `nsw_la_1979plus`); the names are not the jurisdictions' own |
| `valid_from`, `valid_to` | adoption dates, for Debian the day after ratification (above) |
| `ordinance`, `sections` | the ordinance (for Alaska the ballot measure and the regulations with their dates, and the statutes they refer to; for Debian the constitution version with its ratification date; for New South Wales the Schedule of the Constitution Act that holds the count and the Electoral Act in force at each poll, with their dates), and the sections the rules below come from, as a semicolon-separated citation list |
| `overvote`, `skipped`, `duplicate` | `pass_over` (the position is passed over) or `exhaust` (the ballot stops counting); for `duplicate` also `skipped_ranking` (a later ranking of a candidate already ranked is disregarded and counts as a skipped ranking toward `max_consecutive_skips`, and so does a second or later write-in mark on a ballot; no text settles either, the Division's 2022 reports and, for the write-in mark, its cast vote record do, see below); `na` in a Condorcet count, and for `duplicate` also where the ballot paper gives each candidate one square, so no candidate can be ranked twice (New South Wales) |
| `max_consecutive_skips` | `none` (no limit) or a number: one more blank ranking in a row stops the ballot; `na` in a Condorcet count |
| `batch_elimination` | the tests that defeat several candidates at once, joined by `+`: `test1_next_higher_total_surpass` (a group whose total only equals the next higher total is defeated), `test1_next_higher_total_equal_or_surpass` (it is not), `test2_sum_of_all_ranked_votes`, `undeclared_writeins_defeated_round2`, `filed_writeins_defeated_before_round1` (where a write-in candidate filed for the race and no candidate has more than one-half of the active ballots on the initial count, with all write-ins pooled as one candidate, the write-ins together are defeated on that count when their total is below the leading candidate's by at least 0.5 percent of the two totals together, and round 1 is then counted with their rankings left out; if they are not defeated, each valid write-in candidate is counted as a candidate of its own; one candidate is defeated per round after that); `none` where no test defeats several candidates at once and one candidate, the one with the fewest votes, is excluded per count; `na` in a Condorcet count |
| `threshold` | `floor(votes_cast/(seats+1))+1`, then `; first_round_decided_at_maximum_possible_threshold` where a first-round check against the maximum possible threshold can end the count; or `majority_of_active_ballots_round1_only` (more than one-half of the active ballots elects in the first round only, on the initial count or, after a defeat before round 1, in round 1; after it the count goes on until two candidates remain, see `one_seat_stop`); or `majority_of_active_ballots_every_count` (more than one-half of the ballots not exhausted elects, on the first count and on every later count); `na` in a Condorcet count |
| `surplus_transfer`, `surplus_decimals` | `fractional_all_votes_truncated`: every vote of an elected candidate moves on at the surplus fraction times its current value; the surplus fraction and each transfer value are truncated to `surplus_decimals` places; `na` for a one-seat rule set without surplus transfer and in a Condorcet count |
| `last_defeat_transfer` | the votes of the final defeat, the one that leaves as many continuing candidates as seats still to fill: `not_when_continuing_equals_seats_to_fill` (not transferred, as the text says) or `city_sheet_no_transfer` (not transferred, as the city's sheets show, although the text transfers them); `na` where the count stops at two continuing candidates before any such defeat, and in a Condorcet count |
| `one_seat_stop` | when a one-seat count ends if no candidate reaches the threshold: `one_continuing` (one continuing candidate is left) or `two_continuing` (two are left and the one with more votes is elected); `na` in a Condorcet count |
| `default_option` | in a Condorcet count, the `item` of the option the quorum and the majority are tested against; two, separated by `;`, where the rule set's kinds of vote differ, each table holding one of them (in Debian before 2022-01-29 `further discussion` in a General Resolution and `none of the above` in a Project Leader election); `na` in a ranked-choice count |
| `quorum` | `three_q_over_default`: an option other than the default is dropped unless at least R ballots rank it above the default, where R = 3Q and Q is half the square root of the vote's `developers` in `counting_values.csv`, not rounded; `na` in a ranked-choice count |
| `majority_test` | how an option other than the default must beat it, where V(A,B) is the number of ballots that prefer A to B and N the option's `majority` in `counting_values.csv` (N = S for `S:1`, and 1 for an option without a row): `ratio_strictly_greater` (V(A,D) > N * V(D,A)) or `ratio_or_more_and_strictly_greater` (V(A,D) >= N * V(D,A) and V(A,D) > V(D,A)); an option that fails is dropped; `na` in a ranked-choice count |
| `condorcet_method` | `schwartz_sequential_dropping`: a ballot prefers a ranked option to an unranked one and a smaller rank to a larger, while equal ranks and two unranked options give no preference; among the options not dropped, A defeats B when V(A,B) > V(B,A); A is in the Schwartz set when, for every option B, A defeats B directly or through a chain of defeats or B does not so defeat A; while defeats remain inside the Schwartz set, the weakest of them are dropped (fewest ballots for the winner of the pair, then most against it, all equally weak ones at once) and the set is formed again; the one option left wins, and several left go to the casting vote (`evidence`); `na` in a ranked-choice count |
| `source_url` | the official texts, separated by spaces |
| `evidence` | the reasoning behind the row, as in `design_tables.csv`: for Alaska, Debian and New South Wales which text each cell rests on, cell by cell, then how the points the texts leave open are settled; empty for the Minneapolis rows |

Where the 2009 Minneapolis text and the city's sheets disagree, the record follows the sheets. They disagree on the final defeat. The 2009 text (167.70(a)(1)c and e) transfers the votes of every defeated candidate, while the city's sheets for Board of Estimate and Taxation and Park Board at-large show the final defeat moving no votes; a count that follows the words elects the same people with different figures in the last round. `one_seat_stop` records a difference between rule sets, not between text and sheet: the 2009 text ends a one-seat count at two continuing candidates, as the city did in Park District 5, and the 2013 and later texts would go on to defeat the second one. Each date, section and rule cell rests on a quote of the saved ordinance texts, and `city_sheet_no_transfer` on the city's sheets; the table of quotes is available from the contributors on request (#3165). `minneapolis/recount.py` counts by the same three rule sets.

For Alaska each rule and section cell rests on a quote of the saved statute and regulation texts, and `valid_from` on the Division's official results of the 2020 general election (Ballot Measure No. 2, 3 November 2020). Four cells also quote the Division's 2022 General Election Media Packet (`batch_elimination`, `threshold`, `surplus_transfer` and `surplus_decimals`), and two rest on the Division's own 2022 documents and records for a point the texts leave open. In `batch_elimination`, leaving the write-in rankings out of round 1, and so making the test before it, rests on the media packet ("rankings for them will be excluded, meaning they will not be considered") and on the RCV Detailed Reports, which print no write-in line in round 1; 6 AAC 25.071 itself speaks of "the first round of tabulation". The same setting, "Exclude unresolved write-ins", with AS 15.15.360(d)(3), has the first write-in mark on a ballot in a race where no write-in candidate filed count for nobody and be passed over, not read as a skipped ranking ("a ranking for a write-in will not be considered a blank or skipped ranking"), as `evidence` says. In `duplicate`, 6 AAC 25.072 counts a duplicate ranking at its highest ranking and has the board "disregard the remaining rankings for that candidate", and no text says whether a disregarded ranking is a blank one. With it read as one (`skipped_ranking`), and with the write-in rule below, all 13 contests the Division tabulated in rounds in 2022 equal its certified RCV Detailed Reports in every round, against 7 of 13 with a duplicate passed over (for House District 15 and Senate District E the certified reports of November; the recount reports of December 2022 count a different set of ballots). A second or later write-in mark on a ballot also counts as a duplicate ranking. That rests on no statute or regulation but on the Division's own cast vote records, which flag every such mark `DuplicatedRcvCandidate`, as they flag a candidate ranked twice, and on its count, which follows the flag: without it 3 ballots, each with the write-in line ranked three times in a row, would count for a candidate or as an overvote, where the reports of the special and U.S. Senate count them among the Blanks; they are the whole difference between a recount of the tables and those reports. The Division's media packet reads the other way ("a ranking for a write-in will not be considered a blank or skipped ranking"), and `evidence` records both. There is no column for ties: AS 15.15.350(e)(3) resolves a tie between the two candidates with the fewest votes by lot and sends a tie of the final two to AS 15.15.460 and AS 15.20.430 to 15.20.530, cited in `evidence`. `valid_to` is open: the saved history notes show no amendment of 6 AAC 25.071 or 25.072 after 24 February 2022. The statutes are saved as they read today, and AS 15.15.350(c) to (g) and AS 15.40.220 also as the Division's petition page prints the 2020 measure (a transcription, with OCR-type errors elsewhere); the two agree word for word except one "if" in (d)(2) and, in (e)(3), one stop and two capitals ("In" for "in"), besides one dash and two apostrophes printed as different characters, which no saved source explains and no count depends on. No saved source gives the statutes' wording in 2022 or 2024.

For Debian each cell rests on a quote of the constitution's versions as debian.org keeps them (1.1 to 1.9), and the per-vote values on the results pages. The counting method of §A.6 (§A.5 from 1.8) came in with constitution 1.1, ratified 2003-06-21, in place of 1.0's Concorde Vote Counting, and two later versions change a cell: 1.6, ratified 2015-12-13, makes the test against the default "greater or equal to N * V(D,A) and V(A,D) is strictly greater than V(D,A)", so that an option with a supermajority passes at exactly its ratio, and 1.8, ratified 2022-01-28, makes the default of a General Resolution "None of the above" in place of Further Discussion. 1.2 to 1.5, 1.7 and 1.9 change no counting clause; 1.2 adds a kind of decision that needs 3:1, which reaches a count only through an option's `majority`. A count of the 33 Debian tables with these rows and `counting_values.csv` gives the count their 33 results pages print: all 674 cells of the pairwise matrices, the 20 options dropped for majority in 12 votes (none for quorum), the Schwartz sets and the winners. The 2006 Project Leader election is counted with the 984 developers its quorum lines use (below), and the 2007 one prints no majority line, so its two drops are the options its list of defeats leaves out. No vote needed a defeat dropped; one, `debian_2021_gr_fsf_statement`, has a cycle among three options below its winner, outside the Schwartz set. No drop or winner of the 33 changes when the test of 1.1 to 1.5 replaces that of 1.6. There is no column for ties: §A.6(8) leaves several options left in the Schwartz set to "the elector with the casting vote", for a General Resolution the Project Leader (§4.2(4)), and no vote of the 33 left more than one.

For New South Wales each counting cell rests on a quote of the Constitution Act 1902, Seventh Schedule, which the Electoral Commission's 279 preferences pages of 2015, 2019 and 2023 name as "The legislation defining the LA count", and the reading of a ballot paper on the Parliamentary Electorates and Elections Act 1912 (the 2015 poll) and the Electoral Act 2017 (the 2019 and 2023 polls). The Schedule has the same words in the versions in force on the three poll dates, and its history note names only its insertion ("Seventh Sch: Ins 1979 No 38, Sch 1 (6)."). The 2017 Act changes no cell either: it treats a repeated preference or a break in the order after a single 1 as if the later preferences were not recorded (s 165(3)(b)), where the 1912 Act only keeps such a paper formal (s 122A(2)), and the Schedule says the same at all three dates (cl 2(3)). So one rule set covers the 279 tables, with the citations of both Acts in `ordinance` and `sections`. Counted with this row from the tables, the winner and the order of exclusions match the Commission's published distribution of preferences in all 279, and every count matches in 12; the other 267 first differ at count 1, by the 2,695 Formal papers whose ticks or crosses beside a 1 (or beside a tick) the builder places at position 1, where the Commission disregards them: two or more crosses beside a 1, and crosses beside a tick, by the Acts' words (1912 Act s 122A(5), 2017 Act s 165(3)(e)); one cross and nothing else, other numbers and crosses, or a tick beside a single 1, which no section reaches, by the Commission's 2015 data entry rules only (1,364 papers of 2015). Counted from the Commission's marks as recorded, read by the Acts' words and, for those 1,364 papers, by the 2015 data entry rules, every count of all 279 matches, and that reading equals the Commission's `PrefCounted` on all 13,658,150 Formal papers. There is no column for ties: cl 10(1)(a) excludes the tied candidate with the fewest votes at the last count at which they differed, and cl 10(1)(b) and 10(2) otherwise draw a slip; the one tie in the 279, `rcv_nsw_20190323_la_newcastle` at count 1, has no earlier count, and the page excludes c06 and prints no draw. Formality has no column either: the tables carry the Commission's ruling in `cov_formality`, and three patterns beside a single 1 (one cross and nothing else, other numbers and crosses, a tick) were Formal in 2015 under the Commission's 2015 data entry rules (1,364 papers) and Informal in 2019 and 2023 (1,910 and 1,702 papers), although the two Acts' words on such marks are the same.

## Counting values (`counting_values.csv`)

Some numbers a count needs belong to the vote, not to its rule set: Debian's quorum rests on the number of developers when the vote was held, and each option's required majority is set option by option. They are in `counting_values.csv`, one row per value, joined to a table by `table` and, for a value of one option, by `item` (Ben, 2026-10-28, #3024).

| column | |
|---|---|
| `table` | as in `design_tables.csv` |
| `item` | the table's own `item` string, for a value of one option; empty for a value of the whole table |
| `quantity` | what the value is: `developers` (the number of current Developers, which gives the quorum's Q; whole table) or `majority` (an option's required majority, `S:1`; an option without a row needs 1:1) |
| `value` | the value the count used |
| `evidence` | where the value comes from, quoted, as in `counting_rules.csv` |
| `source_url` | the page the value comes from |

The Debian values are those each results page prints: the developer count of its quorum section, and the majority of each option above 1:1 (17 options in 9 votes, all 3:1). The 2006 Project Leader election prints 972 developers but tests every option against 3Q for 984; the file records 984, the number the count used, and `evidence` gives both. Which option needs a supermajority is the ruling printed on each page, and §4.1 of the constitution gives the kinds of decision that need one.

## Validator (`irw_validate/rankings.py`)

| rule | |
|---|---|
| R1 | `id`, `task`, `item`, `resp` present, none missing |
| R2 | `resp` and `task` are positive integers |
| R3 | within `id × task`, no repeated `resp` |
| R4 | `item` is non-empty; the only parenthesised values are `(write-in)` and `(overvote)`; candidate codes have one width; no value looks like a personal name |
| R6 | columns are the four above plus `cov_` and `trial_`; a `cov_` column is constant within a ballot |
| R7 | with `--design`: a design row exists and no `resp` exceeds `n_positions` |
| R8 | with `--design`: the table's candidate-code count and id count match `n_candidates` and `n_ballots_with_marks` |
| floor | fewer than 50 ids warns (the rankings floor; core uses 100) |

It also reports duplicate marks, ballots with a gap, and the marks-per-ballot distribution. (R5 is reserved for the ballot-weight rule, below.)

## Source formats known so far

- **Position-major** (FairVote): one row per ballot, `rank1..rankK` holding names or tokens. Tokens observed: `skipped`, `overvote`, `writein` / `Write-in` / `Write-In`; `undervote` is treated as a skip. Any other lowercase single-word value is reported by the script as a suspected token and should be added to `KNOWN_TOKENS` after checking. Ballot-level columns seen: `ballotID`, `Index`, `Cast.Vote.Record` (row keys, dropped); `precinct(s)`, `ward`, `Ballot.Style`, `ballot_type`, `countingGroup`, `district`, `districtType`, `precinctPortion`, `votingLocation`, `tally_type` (kept as `cov_`); `source_file` (dropped).
- **Candidate-major** (Australian Electoral Commission Senate formal preferences): one row per ballot, one column per candidate holding the preference number. Same layout after pivoting; a script for it is a second batch.
- **Jury-major** (MIRoVision Eurovision jurors): one row per voting jury × entry, one column per juror holding the rank. `eurovision_jurors.py` pivots it; a juror never ranks their own country's entry, so that entry is simply absent from their rows (not a skip).
- **Weighted profiles** (Scottish council elections, PrefLib): one row per distinct ranking with a count. **R5 (Ben, 2026-10-15):** expand to one `id` per ballot, no weight column. The expansion is exact (count and ranking are both given), so nothing is added or lost, and the script reports the number of distinct rankings so the compressed form is recoverable. `id` is one ballot everywhere else in the family, `n_ballots_with_marks` must equal the id count (R8), and a council ward is at most a few tens of thousands of ballots, so the cost is rows, not meaning. `scottish_stv.py` does this; the first table (`rcv_aberdeen_20170504_ward11`, 64 distinct rankings, 6,116 ballots) is built and held until the ruling and the licence are settled.
- **Candidate-major scored** (Voter Autrement 2017): one row per participant, one column per candidate holding a score 11 = first .. 1 = last, blank = not ranked; position = 12 - score. **Candidate-major ranked** (Voter Autrement 2022): the same with the rank itself, 0 = not ranked.
- **Ranking strings** (Voter Autrement 2024): `"1. LIST ; 2. LIST ; ..."` in one cell, split on `" ; "`; a two-choice file (`first_choice`, `second_choice`) is a two-position ranking.
- **Compilations** (Political Rankings Database): one row per respondent, one column per ranked item holding the position, NA for unranked, plus a `ranking` summary string, a 0-indexed `treat` and study covariates. The layout needs no inference; the work is provenance. A compilation carries no licence of its own, so each table is admitted on its **originating study's deposit** (originator rule) and the dictionary row names both, with the compilation in `Source via`. Two things to check in any compilation: whether a file is a treatment-arm **subset** of another (19 of the PRD's 52 are) and whether an NA means "the respondent stopped ranking" or **"the authors released only some items' positions"** -- `fielding_2018_party_ranking` (2 of 7 parties) and `krupnikov_2019_issue_importance` (2 of 6 issues) are the second kind, and say so in the design record, the dictionary description and the processing note.
- **Survey rank widgets** (Qualtrics, YouGov .sav): one column per option holding its position, not ranked as blank, `-99` or NaN; a `_DO` column or `*_row_rnd` variable gives the randomised display order (kept as `trial_display_order` when per respondent). The widget forces a permutation, so a repeated position is a data error, not an overvote: those rankings are dropped and counted in the design record's `evidence` (12 of 550 in one Atsusaka & Kim 2025 question).

## Using the tables

- A person × item pivot is not safe without first handling duplicate marks and gaps: run `irw_rank_compress()` / `irw.rank_compress()` first. `irw_fetch(dedup = TRUE)` and `irw.fetch(dedup=True)` leave rankings tables alone for the same reason.
- Plackett–Luce and Mallows fits want each ballot's ordered list of items by `resp`; overvote rows and write-in rows are usually dropped first.
- Exhaustion and truncation analyses need `n_positions` and `n_candidates` from the design record, and `n_ballots_with_marks` as the denominator, not `n_ballots_cast`.
